# web-edge

Один Docker-образ с **Caddy + Coraza/OWASP CRS + Anubis + CrowdSec** и небольшой
CLI-мастер для публикации веб-сервисов. Укажите домен, поддомен и адрес приложения:
CLI подготовит конфигурацию, проверит её и запустит контейнер. Регистрация в SSO
не нужна. Можно публиковать несколько сервисов на одном сервере.

```text
Браузер → HTTPS → CrowdSec → лимиты → Anubis → WAF → ваше приложение
```

## Установка

Нужен Linux с Docker Engine, свободные TCP 80/443, доступ к backend по сети и
собственный домен. Рекомендуется от 2 CPU / 2 ГиБ RAM. Пакет CLI поддерживает
Debian/Ubuntu, архитектуры amd64 и arm64. Docker Engine устанавливается отдельно
по [официальной инструкции](https://docs.docker.com/engine/install/).

Скачайте `.deb` своей архитектуры и `SHA256SUMS` из
[Releases](https://github.com/k1dory/web-edge/releases). В каталоге со скачанными файлами:

```sh
sha256sum --check --ignore-missing SHA256SUMS
sudo apt install ./web-edge_0.1.0_amd64.deb
sudo web-edge setup
```

Для arm64 замените `amd64` на `arm64`. Пакет устанавливает CLI; первый запуск
скачивает один архив образа из GitHub Releases, проверяет SHA-256 и загружает
его в Docker как `web-edge:0.1.0`. Сервисы автоматически
запускаются после перезагрузки через Docker restart policy.

Мастер спросит:

1. Домен публикаций, например `gw.example.com`, и email для сертификатов.
2. Hostname и внутренний IP **сервера** для журналов.
3. Поддомен, например `nas`, и backend, например `https://10.20.0.10:443`.
4. Профиль `web`, `qnap` или `qnap-share` и нужна ли поддержка самоподписанного
   сертификата backend. Проверка TLS по умолчанию включена.
5. Применить конфигурацию сейчас или только сохранить её.

У регистратора направьте `nas.gw.example.com` и `botcheck.gw.example.com` на
публичный IP сервера. Вместо отдельных записей можно создать `*.gw.example.com`.
Если существует AAAA, IPv6 тоже должен вести на этот сервер. При NAT пробросьте
TCP 80/443 на него. Сертификаты на **конкретные имена** Caddy выпустит и будет
продлевать автоматически; DNS API и wildcard-сертификат не требуются.

```sh
sudo web-edge add              # следующая публикация
web-edge list
web-edge doctor               # DNS и доступность backend
sudo web-edge status
sudo web-edge logs
```

## Пример без диалога

```sh
sudo web-edge setup \
  --zone gw.example.com --email ops@example.com \
  --node edge01 --host-ip 10.20.0.5 \
  --name nas --upstream https://10.20.0.10:443 \
  --profile qnap-share

sudo web-edge add --name wiki --upstream http://10.20.0.11:8080
sudo web-edge edit wiki --waf detect
sudo web-edge remove wiki
```

`--no-start` только сохраняет конфиг. `--tls internal` при `setup` включает
внутренний CA для тестов: браузер не доверяет ему автоматически. `--bot-check=false`
отключает проверку браузера для API/автоматических клиентов. `--waf detect` только
записывает срабатывания, `block` блокирует, `off` выключает WAF.

Конфиг: `/etc/web-edge/config.json`, [пример](examples/config.json). После ручного
редактирования: `sudo web-edge up`. Перед заменой работающего контейнера CLI
проверяет новый конфиг в отдельном контейнере без сети и рабочих ключей. Применение
перезапускает единый контейнер, поэтому на несколько секунд затрагивает все сайты.
При неудачном старте CLI восстанавливает предыдущий конфиг и образ; миграции данных
при обновлении сторонних компонентов этим механизмом не отменяются.

## Профили QNAP

- `qnap` — полный веб-интерфейс QTS; отдельные лимиты `authLogin.cgi`, до 1 ГиБ
  тела одного HTTP-запроса и узкое исключение известного ложного срабатывания CRS.
- `qnap-share` — только `/share.cgi` с непустой query и GET/HEAD статических
  ресурсов страницы шаринга. Корень, форма входа и административные CGI закрыты
  ответом 404. Ссылки сохраняют исходные параметры. Это не авторизация ссылки:
  срок действия, пароль и разрешения проверяет сам QNAP.

Пути статики проверены на интерфейсе QTS с ExtJS 3.3.3. Для другой версии может
потребоваться адаптация allowlist. Просмотр и скачивание по общим ссылкам не
должны требовать открытия административных CGI. Создайте тестовую ссылку и
проверьте нужные сценарии перед переключением клиентов.

## Защита и границы

Anubis выполняет proof-of-work, cookie действует 24 часа и привязана к IP;
атрибуты Secure/HttpOnly/SameSite=Lax. Смена IP потребует новой проверки. Явно
обозначенные сканеры/headless-браузеры получают отказ, но User-Agent подделывается,
а PoW может решить и бот. Общий лимит — 600 запросов/минуту/IP. Для login paths —
20/минуту и 100/15 минут, включая проверки сессии; люди за одним NAT делят бюджет.
Лимиты и размер запроса меняются в конфиге. По умолчанию WAF работает в block/PL1.

CrowdSec анализирует локальный access-лог и исполняет локальные решения.
Автоматическая регистрация в Community API и отправка сигналов в сообщество
не включены. Ключ bouncer и ключ Anubis создаются отдельно для каждой установки.

```sh
sudo web-edge block 203.0.113.25 4h
sudo web-edge decisions
sudo web-edge unblock 203.0.113.25
```

Решение приходит в Caddy примерно за 5 секунд и действует на всех публикациях.
Неудачные пароли нельзя считать по HTTP 200 от QNAP: для этого нужен его журнал
аутентификации. Ограничение количества запросов работает независимо от этого.

Caddy перезаписывает `X-Real-IP` и `X-Forwarded-For` адресом соединения, удаляет
входящий `Forwarded`. Доверенных внешних прокси нет. Ставьте его непосредственно
на входе; установка за CDN/другим прокси требует отдельной настройки доверия.
В Linux Docker bridge обычно сохраняет внешний IP при публикации портов;
Docker Desktop/rootless-прокси/другие NAT могут его заменить — проверьте access-лог.
Backend на уровне TCP видит адрес прокси. Передача заголовков не гарантирует,
что штатный бан конкретного NAS умеет ими пользоваться.

Оставленные прямые пробросы к backend обходят эту защиту. Ограничьте доступ к
backend адресом reverse proxy после проверки публикации. `--insecure-upstream`
явно отключает проверку сертификата backend; предпочитайте доверенный сертификат.

## Hostname, IP сервера и контейнер в журналах

Все stdout/stderr сервисов оборачиваются в JSON с отдельными полями:

```json
{"timestamp":"2026-01-01T12:00:00Z","node":"edge01","host_ip":"10.20.0.5","container":"web-edge","service":"caddy","message":"..."}
```

`identity.node` и `identity.host_ip` задаёт CLI **на хосте**, поэтому имя узла
не берётся из Docker-сокета Coraza или HTTP Host посетителя. Адрес сокета внутри
строки WAF сохраняется отдельно. Для ARGUS см. [пример Vector](examples/vector-argus.yaml):
он создаёт готовые события для `/ingest/events` с `node`, `attrs.host_ip`,
`attrs.container` и `attrs.server_addr`/`dst_ip`, обходя неоднозначный разбор
`[hostname]` старым syslog-нормализатором. Vector запускается на хосте отдельно;
Docker socket не монтируется в web-edge.

Полный audit JSON с телами запросов выключен; срабатывания остаются в error-логе
Coraza. Access-лог хранится в `/data/logs/access.json` с ротацией 20 МиБ × 5.
Сообщения правил и URI могут содержать чувствительные данные — ограничивайте
доступ к журналам и срок их хранения.

## Данные и обновление

Сертификаты, ключи и база CrowdSec живут в Docker volume `web-edge-data`. `down`
останавливает контейнер и сохраняет данные. Перед обновлением сохраните конфиг
и резервную копию этого тома. Не удаляйте его для обычного обновления.

```sh
sudo apt install ./web-edge_VERSION_amd64.deb
# Новый CLI скачает соответствующий образ по контрольной сумме:
sudo web-edge up --image web-edge:VERSION
```

Публичны только HTTP/HTTPS. Admin API Caddy, CrowdSec LAPI и Anubis слушают loopback
внутри контейнера. Контейнер работает под UID 10001 без capabilities, с read-only
корнем и без Docker socket; падение одного сервиса завершает весь контейнер.

## Сборка и проверки

```sh
go test ./...
go vet ./...
docker build -t web-edge:dev .
python3 scripts/package.py --version 0.1.0
python3 scripts/smoke.py --image web-edge:dev
```

Тесты Docker используют только синтетический backend в отдельной сети, отдельные
тома и внутренний CA. GitHub Actions проверяет исходники, собирает amd64/arm64,
публикует архивы образа, CLI-пакеты и контрольные суммы в Releases по тегу версии.
